# Правила проекта mts_ads

## Базовые принципы

- Используем актуальные best practices React и Vite: маленькие компоненты, чистый render, явные зависимости, минимальная глобальная мутация.
- Архитектура строится через composition: страницы собираются из feature-блоков, feature-блоки из компонентов, компоненты получают данные через props и callbacks.
- Не используем `export default`. Все модули экспортируют именованные сущности, чтобы импорты были однозначными и хорошо искались по проекту.
- Файлы с UI-компонентами называем по имени экспортируемого компонента: `CampaignTable.jsx`, `AdCard.jsx`, `BudgetControl.jsx`.
- Стили держим рядом с уровнем ответственности компонента или в общих design tokens, если они используются повторно.

## Composite architecture

- `src/app` - инициализация приложения, провайдеры, роутинг, глобальные shell-компоненты.
- `src/pages` - route-level композиции без бизнес-логики ниже feature-уровня.
- `src/features` - бизнес-сценарии: кампании, объявления, бюджеты, аналитика.
- `src/entities` - предметные модели и UI вокруг одной сущности.
- `src/shared` - переиспользуемые primitives, hooks, utils, api-клиент, constants.
- Каждый слой может импортировать только более низкие или соседние публичные API, а не внутренние файлы другого feature.

## React

- Компоненты должны быть чистыми: JSX зависит от props, state и локальных вычислений, без побочных эффектов в render.
- Side effects размещаем в handlers, async actions или `useEffect`, если эффект синхронизирует компонент с внешней системой.
- State держим как можно ближе к месту использования; поднимаем его только при реальной общей зависимости.
- Производные значения вычисляем из state/props, а не дублируем в отдельном state.
- Списки рендерим со стабильными ключами из данных, не с индексами массива, если порядок может меняться.

## Vite

- Переменные окружения для клиентского кода должны начинаться с `VITE_`.
- В `public` кладем только статичные файлы, которым нужен стабильный URL без обработки bundler.
- Импорты assets из `src` используем для файлов, которые должны пройти через pipeline Vite.
- Production-проверка перед сдачей: `npm run lint` и `npm run build`.

## Качество кода

- Предпочитаем named exports/imports, маленькие модули и явные публичные API через `index.js`.
- Не добавляем абстракции заранее; выносим общую логику после повторного использования или явной сложности.
- UI должен быть доступным: semantic HTML, `button` для действий, `a` для навигации, понятные `aria-*` только когда семантики HTML недостаточно.
- Ошибки и loading states проектируем как часть сценария, а не как временную заглушку.
